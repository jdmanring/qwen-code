# Prompt Architecture Implementation Guide: Qwen Code

This guide defines how Qwen Code constructs prompts to ensure operational control, consistent output, and efficient token usage.

---

## 1. The Prompt Hierarchy (The Layered Approach)

Qwen Code does not send raw user queries to the LLM. Instead, it constructs a layered prompt that wraps the user's intent in operational constraints.

### Construction Sequence (Top to Bottom)

| Layer | Source | Purpose |
| :--- | :--- | :--- |
| **Identity Layer** | `config/agents/[agent].md` | Establishes the expert role, goals, and behavioral boundaries. |
| **Global Constraints** | `QWEN.md` | Injects global rules (e.g., `S-READ`, `P-AUTH`) that override role-specific behavior. |
| **Fast-Activation Anchor** | `QWEN.md` (Top) | High-density summary of critical mandates to combat "Lost in the Middle" effect. |
| **State Context** | Dynamic (`packages/core`) | Provides real-time operational state: Current Phase, Todo List, and Runtime Variables. |
| **Conversation History** | Session History | Provides a pruned window of previous turns for context. |
| **Query Layer** | User Input | The specific task or question the user is asking. |

### The Fast-Activation Pattern (Global Anchoring)

To ensure strict adherence to the most critical mandates, Qwen Code employs a **Fast-Activation Anchor** at the top of `QWEN.md`.

**Technical Rationale:**
LLMs exhibit a U-shaped retrieval curve, known as the **"Lost in the Middle"** phenomenon (Liu et al., 2023). Information located at the very beginning (Primacy Effect) and very end (Recency Effect) of a prompt is recalled and followed with significantly higher fidelity than information in the center.

**Implementation:**
By condensing the project's non-negotiable "Operational Laws" into a high-density cheat sheet at the top of the global constraints file, we:
1. **Set Global State**: Immediately activate the correct operational persona.
2. **Prevent Drift**: Ensure that critical safety and quality rules (e.g., No Blind Iteration, ASCII-only) are not lost as the context window grows.
3. **Optimize Token Attention**: Focus the model's initial attention on the "Hard Constraints" before it parses detailed documentation.

## 2. Technical Implementation

Prompt construction is primarily handled in `packages/core/src/core/prompts.ts`.

### Core System Prompt
The `getCoreSystemPrompt` function generates the base identity of the agent.
- **Default**: A hardcoded set of "Core Mandates" including conventions, proactiveness, and tool usage rules.
- **Override**: If the environment variable `QWEN_SYSTEM_MD` is set, the system loads the prompt from the specified file path.

### Custom System Prompts
The `getCustomSystemPrompt` function allows for dynamic extension of the system prompt. It follows this concatenation order:
1. **Custom Instruction**: The base role or task-specific instruction.
2. **Deferred Tools**: A list of available tools that must be discovered via `tool_search` (see below).
3. **User Memory**: Persistent user-specific preferences or context.
4. **Append Instructions**: Any final, high-priority constraints.

---

## 3. Special Prompt Features

### Deferred Tools
To prevent the system prompt from becoming too large, the system uses a **Deferred Tool** mechanism.
- **Mechanism**: Instead of including full JSON schemas for every tool, the prompt includes a lean list of tool names and short descriptions.
- **Discovery**: The model is instructed to call `tool_search` to fetch the full schema of a specific tool before attempting to use it.
- **Security**: Tool descriptions are JSON-encoded to prevent prompt injection where a tool description might attempt to override system instructions.

### User Memory Injection
User-specific memory is appended to the system prompt using a consistent delimiter:
```markdown
---
[User Memory Content]
```
This ensures the model distinguishes between global rules and user-specific preferences.

## 4. Programmatic Enforcement

Prompting is the "soft" control. To ensure "hard" safety, the system uses the **Policy Engine**.

- **Location**: `packages/core/src/policy_engine.py`
- **Function**: The Policy Engine intercepts every tool call generated by the LLM. It checks the `intent` and `agent_name` against a permission matrix to block unauthorized actions regardless of what the prompt told the AI to do.

## 5. Developer's Guide to Extension

### Modifying Global Constraints
To change the behavior of all agents across the system, modify `QWEN.md`. These rules are injected into the core identity of every agent.

### Creating a New Agent Role
1. Create a new markdown file in `config/agents/[agent-name].md`.
2. Define the role's expertise, primary goals, and specific constraints.
3. The `AgentGeneratorService` will automatically wrap this role in the global constraints.

### Adding New Prompt Layers
To add a new layer to the prompt construction:
1. Modify the prompt construction logic in `packages/core/src/core/prompts.ts`.
2. Ensure the new layer is placed correctly in the hierarchy (e.g., state context should generally come after identity but before the query).

## 6. Verification Checklist

- [ ] **Hierarchy Order**: Does the final prompt follow the Identity $\to$ Constraints $\to$ State $\to$ History $\to$ Query sequence?
- [ ] **Token Efficiency**: Are large toolsets being handled via the Deferred Tools mechanism?
- [ ] **Injection Safety**: Are dynamic inputs (like tool descriptions) properly encoded to prevent prompt leakage?
- [ ] **Policy Alignment**: Does the Policy Engine's permission matrix align with the instructions given in the prompt?
